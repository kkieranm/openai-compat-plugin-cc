# OAI-221 — evidence

Measurements from a two-day investigation, 2026-08-25/26, that began as "how far are we from running
a local model as a review-ladder stage" and ended by finding that a single unreachable setting
decides whether local review works at all.

Nothing here is inferred. Every figure is from a `bench/` run whose record is in `bench/results/`,
or from a direct API probe reproduced in the text. **The corrections section is not an appendix** —
several claims in this file's own earlier drafts, and several reported to the owner during the run,
were wrong, and the record is only useful if it says which.

## The headline

A reasoning model's thinking channel is controlled by the chat template's `enable_thinking`
variable. `scripts/lib/client.mjs` cannot send it, `chat_template_kwargs` is not honoured by LM
Studio, and the only route is the server's per-model configuration. Four models were scored on the
full corpus with it ON and again with it OFF, everything else identical, each verified at
`reasoning_tokens=0` immediately before its run:

| model | thinking ON | thinking OFF |
|---|---|---|
| `qwen/qwen3.8-27b` | 0/6 cases, every one timed out, ~2,100s | 4/6 cases, 1 anchored, clean control |
| `qwen/qwen3.6-35b-a3b` | 2/6 cases, 1 anchored, 1,595s | 5/6 cases, 1–5 anchored, **319s** |
| `google/gemma-4-26b-a4b` | 4/6 cases, 1 anchored | 4/6 cases, 1 anchored, 0 unmatched |
| `gemma-4-12b-it-mlx` | *already off — no hub config overrode the template default* | 5/6, 1 anchored |

Generation time collapsed from hundreds of seconds to 1–34s per case. Prefill then dominates, which
is a hardware property rather than a model one.

**Every other lever measured across ~110 review invocations moved availability or latency at best,
and none moved capability**: `reasoning_effort` (`low`/`medium`/`xhigh`), temperature,
`top_p`/`top_k`/`min_p`, quantization from 2-bit to 6-bit, reply budgets, `--structured-output`,
`--parallel` 1/4/8, and prompt phrasing.

## The ranking, thinking OFF, N=1 each

Full corpus, `--runs 1 --cold --max-seconds 300`, all four models installed at the time:

| model | cases | anchored | where | unmatched | control | time |
|---|---|---|---|---|---|---|
| `gemma-4-12b-it-mlx` | 5/6 | 1 | config-origin | 1 | clean | 801s |
| `qwen/qwen3.6-35b-a3b` | 5/6 | 1 | **scaffold** | 36 | clean | 319s |
| `google/gemma-4-26b-a4b` | 4/6 | 1 | config-origin | 0 | clean | 305s |
| `qwen/qwen3.8-27b` | 4/6 | 1 | config-origin | 0 | clean | ~2,000s |

## Replication, and why the N=1 row above is misleading

`qwen/qwen3.6-35b-a3b`, thinking off, three runs of the identical configuration:

| run | anchored | cases matched | control FPs |
|---|---|---|---|
| 1 | 1 | scaffold | **0** |
| 2 | **5** | config-origin ×2, model-info, scaffold ×2 | **4** |
| 3 | 3 | config-origin, scaffold ×2, caps 1/1 | **2** |

Two conclusions, and they pull in opposite directions. Its **recall is far higher** than run 1
showed — it anchors defects in four of the five code cases, not one. Its **control is clean in only
1 run of 3**, so the clean control in run 1 was the unrepresentative draw, not the finding.
Thinking-off makes this model substantially more capable *and* substantially noisier.

`gemma-4-12b-it-mlx` replicated exactly: 5/6, 1 anchored on config-origin, clean control, 1
unmatched, twice.

## Corrections and retractions

Recorded because each was reported as a finding before being falsified.

- **"Every anchored match comes from `config-origin`; the corpus is effectively one case."** Stated
  repeatedly on ~110 invocations of evidence. **False.** With thinking off, `qwen/qwen3.6-35b-a3b`
  anchors in `scaffold`, `model-info` and `caps` as well.
- **"The gemmas ran with reasoning off."** Inferred from the template's `enable_thinking |
  default(false)`. Wrong for the models that have a hub `model.yaml` setting it true; right only for
  `gemma-4-12b-it-mlx`, which has none. Config was inferred from a file rather than measured.
- **"`--structured-output` fixes qwen3.8."** Called a breakthrough on one two-case run. Reproduced
  2 of 3 on fresh loads, and 0/6 on the full corpus. It helps; it is not a fix.
- **"Greedy decoding breaks qwen reasoning models and leaves gemmas untouched."** Withdrawn — the
  runs behind it went through a contaminated proxy (below) and several compared configurations that
  were in fact identical.
- **"Vendor sampling rescued `qwen/qwen3.5-9b`."** Withdrawn, same cause: that run actually carried
  `reasoning_effort: medium` + temp 0.6.
- **A 1,105s run was reported with its lens as whole-file.** Its record says `hunksOnly: true`. The
  whole-file rung needs ~64k estimated tokens and no 27b on this machine can reach it.
- **`--parallel 1` was predicted to free KV cache and yield more context.** It does not: 1, 4 and 8
  all loaded `gemma-4-12b-it-mlx` at exactly 147,456 and produced identical findings.
- **A "6.5 GB swap peak" was attributed to OAI-133.** That item states no such threshold; the figure
  was this session's own reading while a stale model was resident. OAI-133's actual rule is ≥1.5 GB
  headroom.

## Methodological failures

- **Proxy contamination.** Tuning parameters were injected by a scratchpad proxy. Its restart used
  `pkill -f 'scratchpad/proxy.mjs'`, but the process command line was `scratchpad/tuned/../proxy.mjs`
  — the pattern never matched, the old proxy survived, and each new one died on `EADDRINUSE`. **Only
  5 of 17 proxies ever bound; twelve runs silently used a previous run's injection.** The results
  looked plausible and were reported as findings. Fixed by waiting for the port to release and
  asserting a `/__inject` health endpoint returns the expected configuration before benchmarking —
  which then correctly refused three runs over a `0.0`/`0` JSON round-trip mismatch. Contaminated
  data is archived, not deleted.
- **N=1 reported as result, repeatedly.** A raw-finding-count ranking put `qwen/qwen3.5-9b` first;
  the labelled corpus scored it zero. A two-case structured-output run was called a breakthrough and
  reproduced 2 of 3. The MoE's clean control held in 1 run of 3. Every one of these was a single
  sample presented as a finding before replication.
- **Concurrency was never isolated** until asked about: `--parallel 1` was bundled with greedy arms
  and `--parallel 4` with vendor arms, so the two moved together in every run.
- **A stale 15.14 GB model left resident** for hours caused LM Studio's guardrail to refuse
  subsequent loads; the refusals were briefly attributed to the models rather than to memory
  pressure.

## Tune / hold-out result

Designed after Codex objected that searching a parameter space and reporting on the same six cases
would overstate the result. Screen on `config-origin` + `docs-only`, freeze one configuration per
model, rank once on untouched `caps`, `model-info`, `scaffold`, `structured` (8 defects), no
re-tuning afterwards. Thinking was ON throughout — this predates the discovery.

| config | tuning case | hold-out |
|---|---|---|
| `gemma-4-12b-it-mlx`, temp 0.7 / top_p 0.8 | **2/2** | **0/8** |
| `google/gemma-4-26b-a4b`, vendor sampling | 1/2 | **0/8** |
| `qwen/qwen3.6-35b-a3b`, vendor sampling | 1/2 | **0/8**, all four timed out |

Sampling tuning improved the selected case and generalised to nothing. Note the hold-out figures
are for thinking-ON configurations and are superseded by the replication section above.

## Other measurements worth keeping

- **`--max-seconds` does not bound the command.** `--max-seconds 900` produced a 1,105s run: the
  original request gets the one expiry, and salvage opens a fresh `performance.now() + 300_000`.
  Filed as OAI-216.
- **`lms load --context-length` is silently clamped or ignored per model.** Requesting 262,144 gave
  147,456 with exit 0 and no warning; `qwen/qwen3.8-27b` ignores the flag entirely and pins 61,696.
  Max loadable contexts measured by reading `loaded_context_length` back: qwen3.5-4b 210,432;
  qwen3.5-9b 154,624; gemma-4-12b-it 147,456; gemma-4-e4b 131,072; gemma-4-26b-a4b-qat 116,736;
  qwen3.6-35b-a3b 71,936; both 27b 61,696.
- **The whole-file rung needs ~64k estimated tokens for `f5addcb`**, so it opens only above ~116,736.
  Measured by calling `prepareLadder` directly across windows: the hunks prompt is identical
  (14,405 est) at every window and every reply budget.
- **`preserve_thinking` is inert for this plugin.** The template gates it on
  `message.reasoning_content`; the original review has no prior assistant turn and salvage passes
  reasoning back as `content`.
- **`lms load --estimate-only` cannot find a load boundary.** It returned "may be loaded" for every
  model at 262,144 including one needing 26.64 GiB, and its verdict tracks current machine state —
  the same model flipped from "will fail" to "may be loaded" purely by unloading a stale one.
- **The MLX tokenizer bug reported for Devstral did not appear**: zero `Ġ`/`Ċ` artifacts.

## Unresolved

- **The MoE's precision.** Clean control in 1 run of 3. This is the number that decides whether it
  is usable as a stage and N=3 does not settle it.
- **Whether `--structured-output` recovers the unreadable cases** — `caps` and `structured` are lost
  to OAI-212's parser gap on the gemma models, and a schema bypasses the acceptor. The arms were
  queued and never ran.
- **Sampling with thinking off.** Every sampling measurement was taken with thinking on, where the
  runaway swamped it.
- **Recall beyond one run.** The best single run found 5 of 8 scoreable defects; whether that
  repeats is unknown.
